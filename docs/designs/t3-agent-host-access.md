# Design: Agent host access and pipeline reliability

Generated by /office-hours on 2026-09-08
Branch: fix/revert-stale-dependabot-bumps
Repo: tetracilin/test_ai_todo
Status: DRAFT
Mode: Startup
Supersedes: none (first design on this branch; extends premise 5 of `t3-company-os-ssot.md`)

## Problem Statement

`t3-nightly` failed **every run it had**, from its first on 2026-09-02 until 2026-09-08 — nine
runs, none green. The deploy half was fixed on 2026-09-08 when the operator created the two
missing secret files on kmv8; the 01:24 dispatch deployed successfully and staging now runs
`41c64c62`. The runs still read red, because `slow-tests` fails independently and has never
passed. Three
unrelated causes produced those failures in six days, and a fourth arrived during this
session. The pattern matters more than any single cause:

| Failure | Why the merge gate missed it |
|---|---|
| PR #78 made two host files mandatory; nobody created them (fixed 2026-09-08) | `t3-ci` runs on a GitHub runner and **cannot see kmv8**. The prerequisite lived only in a commit message |
| PRs #80 and #81 broke server tests | `t3-ci` **runs no server vitest** (`t3-ci.yml:95-99`). Those suites are nightly-only |
| PRs #62 and #63 merged red, five days stale, 98s apart | **`develop` has no branch protection**, so red and out-of-date PRs are mergeable |
| e2e has never executed once | `Install Chromium` and `E2E` carry no `if: always()`; the job aborts at the failed vitest step every time |

The merge gate is structurally blind to the deploy host and to the server test suites, and
`develop` accepts anything. This is survivable at human merge rates. The approved charter
(`design.md:85-94`) says the merger will be an agent loop, measured on *merged auto-PRs vs.
regressions/rollbacks* — a metric a batched nightly cannot produce, because it cannot
attribute a failure to one of N merges and no human remembers what landed.

The specific stall this design targets: **the loop dies where the repo ends and the host
begins.** An agent diagnosed the #78 breakage correctly and emitted "create these two files
on kmv8". It could not do that. Neither could the owner, who had not been shown how. Five
days passed with a correct diagnosis and no fix.

## Demand Evidence

- **Observed, this week.** A correct agent diagnosis sat unexecuted for five days because
  its output was a task neither side of the loop could perform. Owner, verbatim: *"agent
  required secret files should be created but i dont know how."*
- **Observed, during this session.** Two Dependabot PRs — the simplest possible "agent that
  authors branches and manages PRs" — took `develop` down at 23:48Z and 23:49Z. Nothing
  between them and the integration branch was capable of saying no. This is the target
  workflow, already running, already failing.
- **Budget allocated, internal paying customer** (`t3-company-os-ssot.md`). The charter is
  approved and funded; only the loop is unbuilt.

## Status Quo

Detection is **not** the gap, contrary to an assumption made and corrected during this
session. A cron on kmv8 mails the owner every morning when the build fails. The owner reads
it. The break still lived five days, because the message names a failure the reader cannot
act on and the pipeline has been red since its first run, so the message never changes.

Note: that cron is almost certainly Hermes `8b51805f9dc5`, which `CICD/PLAN_CICD.md:229`
says to disable at cutover. It is still running. The plan is wrong about that.

## Target User & Narrowest Wedge

**User:** the owner-operator, and the agent acting on their behalf.

**Wedge:** a fixed, reviewed menu of host operations the agent can trigger through the
channel that already exists — GitHub Actions on the `kmv8` self-hosted runner. Not a shell,
not a key. The narrowest thing that would have closed this week's failure without a human
typing a command they had to be taught.

## Constraints

Real, verified, and non-negotiable:

- `CLAUDE.md` — agents never tag, never approve environments, never run anything under
  `deploy/` on kmv8. Pipeline changes get their own PR, labelled `ci`, human-reviewed, never
  mixed with application code.
- **Adapter runtime code cannot `git push`.** `packages/adapters/AUTHORING.md:8-33`,
  statically enforced by `scripts/check-no-git-push.mjs` over `packages/adapters`,
  `packages/adapter-utils`, `server/src`, `cli/src`, wired into `t3-ci.yml:57`. Escape hatch
  is an explicit `// paperclip:allow-git-push: <reason>` marker. **The self-development loop
  cannot live inside the product's own adapters** without taking that escape.
- `t3-ci` is GitHub-hosted only, by design: *"PR code is untrusted until merged"*
  (`t3-ci.yml:2`). Host verification cannot simply be moved into the PR gate.
- `ghrunner` has **no sudo**; it is in the `docker` group, which is root-equivalent on that
  box in practice. Every workflow declares `permissions: contents: read`. No workflow
  anywhere writes to `/etc/t3/secrets` today — all four references are read-only `[[ -s ]]`
  checks.
- `staging` environment has **zero** protection rules. `production` requires reviewer
  `tetracilin`. `enforce_admins` is `false` on `main`.

## Premises

Derived from the session and from verified repo state. Not separately ratified — treat the
last two as the ones most worth arguing with.

1. The three failures are one architecture, not three bugs. Fixing them individually leaves
   the shape intact and the next `#78`-shaped change breaks it again.
2. Detection is adequate; **actionability** is the gap. A daily message naming a fix the
   reader cannot perform is not a working alarm.
3. A pipeline that has never once been green has no baseline, so it cannot produce the
   charter's regression metric. Green once, then defend it, precedes any measurement.
4. Agent merge volume amplifies every gap above. Dependabot demonstrated this during the
   session at a volume of two.
5. Widening agent authority is easy; withdrawing it after a leak is not. Start at the
   narrowest setting that closes the observed failure.

## Approaches Considered

**A. Fixed operation menu** *(chosen)* — a reviewed ops workflow on kmv8 exposing a closed
list of operations via `workflow_dispatch`. The agent triggers listed operations and may
open PRs to add new ones. No SSH key, no new credential.

**B. Approved arbitrary scripts** — the agent authors a script, a human approves the run, it
executes on kmv8 in a scoped sandbox. More general, no menu to outgrow. Rejected for now:
the approval is the only control, `enforce_admins` is `false`, and a reviewer approving a
long shell script at 2am is not a real gate. Reachable later from A.

**C. Shrink what needs the host** — move hand-maintained host state into GitHub Environment
secrets so the agent rarely needs kmv8 at all. Rejected as *the* answer during the session;
retained as a complement — A gives the agent a door, C means it knocks less often.

## Recommended Approach

**A, sequenced behind two things that must come first.**

**Phase 0 — restore a baseline (blocks everything).**
1. ~~Merge PR #91 (reverts #62/#63).~~ **Done 2026-09-08.** `develop` is green again.
2. ~~Create the two artifact key files under `/etc/t3/secrets/nightly/`.~~ **Done 2026-09-08.**
   The deploy job now succeeds and staging runs the current `develop`. Note the files were
   created with placeholder values; the trap in `TODOS.md` stands.
3. Set `DISCORD_WEBHOOK_URL` as a **repository** secret. It must not be environment-scoped:
   `slow-tests` (`t3-nightly.yml:199`) declares no `environment:`, so an env secret is
   invisible to the job whose alert would have caught the test regressions.
4. Add `if: always()` to `Install Chromium` and `E2E` so e2e runs for the first time.
5. Fix the two server-test regressions (`#80`'s `externalObjects` mock gap, `#81`'s
   `status-cards` assertion). Target: **one green nightly**, which has never happened.

**Phase 1 — make the gate able to refuse (repo settings, no code).**
Protect `develop`: require `unit` / `build` / `build-image`, and require branches to be up
to date. This single change would have prevented tonight's incident. It is also the
precondition for letting any agent merge anything.

**Phase 2 — the ops workflow (the chosen wedge).**

- `.github/workflows/t3-hostops.yml`, `runs-on: [self-hosted, kmv8]`, its own `hostops`
  GitHub Environment with a required reviewer, `workflow_dispatch` with a `choice` input.
  Follow the existing input pattern (`t3-nightly.yml:15-20`) — note the repo has no typed
  inputs today, so `choice` is new here.
- Operations as checked-in scripts under `deploy/scripts/hostops/`, reviewed like code, with
  the **exec bit committed** — PR #68 exists solely because a missing mode bit killed a
  nightly with exit 126.
- v1 operation set, deliberately small: `secrets:check` (report presence/emptiness, never
  values), `secrets:provision-missing` (create only if absent, never overwrite),
  `stack:status`, `stack:restart`.
- Invariants, enforced in the scripts: never print a secret value; never overwrite an
  existing file; `prod` target routes through the `production` environment gate.
- Its own PR, labelled `ci`, per `CLAUDE.md`.

**Phase 3 — the loop.** Retarget the existing machinery rather than writing new: `.agents/skills/`
already has `prepare-paperclip-pr`, `prcheckloop`, `pr-gardening` and `doc-maintenance`
(which carries a working `gh pr create` block). All were written against upstream
`paperclipai/paperclip` **master** and need pointing at this fork's `develop`. The loop runs
outside the `check-no-git-push` roots. `scripts/paperclip-commit-metrics.ts` already counts
`Co-Authored-By: Paperclip` commits and is the natural seed for PC-013's auto-PR metric.

## Open Questions

1. **Does `/etc/t3/secrets/prod/` have the two artifact keys?** `t3-release.yml:99-102`
   carries the identical gate and the workflow has never run. PR #78's message asserts prod
   already has them; nobody has looked.
2. **What identity does the agent commit and push as?** No bot account or GitHub App exists.
   The `Co-Authored-By: Paperclip <noreply@paperclip.ing>` trailer convention exists in
   `.agents/skills/`, but nothing issues a push credential.
3. **Is Hermes cron `8b51805f9dc5` still the morning notifier?** If so, `PLAN_CICD.md` §4 is
   wrong that it was retired, and the real alerting path is undocumented.
4. Should `hostops` reuse the `production` reviewer, or have its own?
5. `main` carries `allow_force_pushes: true` and `required_linear_history: true`; the latter
   contradicts the documented "merge commit, not squash" release step. Not urgent —
   `enforce_admins` is `false` — but it will stop the first non-admin release.

## Success Criteria

- One green `t3-nightly`, end to end. Never achieved to date.
- `e2e` executes at all. Never achieved to date.
- `develop` rejects a red or out-of-date PR.
- An agent closes a host-shaped task end to end with no human typing a shell command.
- PC-013 becomes computable: merged auto-PRs, and reverts attributable to them.

## Dependencies

Phase 0 blocks 1, 2 and 3. Phase 1 blocks any agent merge. Phase 2 blocks the agent closing
host-shaped tasks. Phase 3 depends on all three, and on Open Question 2.

## The Assignment

**Turn on branch protection for `develop`** — require `unit`, `build`, `build-image`, and
require branches to be up to date before merging. Repo Settings → Branches. Five minutes, no
code, no agent can do it for you.

It is the one change that would have prevented tonight's incident outright, and it is the
precondition for every later phase. Do it before you merge #91, so #91 is the first PR that
goes through the gate.
