# Design: CEO agent auto-requests MCP access for newly hired agents

Generated by /office-hours on 2026-09-23
Branch: docs/2026-09-23-session-status-update
Repo: tetracilin/test_ai_todo
Status: APPROVED
Mode: Startup (intrapreneurship)

## Problem Statement

MCP access for an agent is already fully governed and resolved automatically at
every heartbeat run (`buildPaperclipRuntimeMcpServers` → `getEffectiveProfilesForAgent`
→ adapter injection, e.g. `packages/adapters/claude-local/src/server/claude-config.ts`).
What's missing is the *grant* itself: nothing in the hiring path
(`POST /companies/:companyId/agent-hires`, `server/src/routes/agents.ts:3139`) attaches
a tool-access profile to a newly hired agent. That step is manual and lives entirely
outside the hire flow, in the Apps/Connections → tool-access UI.

## Demand Evidence

Owner-reported: the manual grant step is the one that actually gets forgotten in
practice — new hires start their first tasks with no or stale MCP access, discovered
after the fact rather than caught at hire time. (Manual-workaround-pain, not yet a
scaled/measured incident count — single small team today.)

## Status Quo

Today: a human (the owner) hires an agent, then separately opens the tool-access UI
to grant it profiles. No system prompt or gate forces that second step, so it's
routinely skipped. The agent runs its first heartbeat with whatever MCP access it
happens to already have (usually none, if newly created).

## Target User & Scope

The owner and a small team operating Paperclip AI companies — anyone hiring agents,
through either creation route (`agent-hires` or the board-direct `POST /agents`).
Both are in scope: see Trigger Mechanism below — hooking the shared agent-creation
service, rather than either route's approval branch, covers both routes by
construction, so this is no longer an open decision. Not (yet) a multi-tenant/
external-customer concern.

## Constraints

- Must reuse the existing tool-access/profile model (`toolProfiles`,
  `tool-access-policy.ts`, `tool-profile-binding-precedence.ts`) — no new
  agent-instance-level MCP schema. Confirmed during premise-check: two agents
  sharing a role are expected to share the same MCP scope; the ask is *automatic,
  timely* application of that existing model, not a more granular one.
- Must respect this repo's governed-action invariant (AGENTS.md §5): mutating,
  consequential actions go through the approval-gate pipeline and get
  activity-logged — a silent system-level auto-bind (no record at all) was
  considered and rejected in favor of an explicit, logged CEO-attributed grant
  request (see Approaches, below).
- MCP injection itself (adapter layer) needs no changes — only the grant step.

## Trigger Mechanism (revised after code-grounded review — v1 of this section was wrong)

**v1 of this doc hooked "the hire-approval transaction."** Round-2 review checked
that against the actual code and found it doesn't exist for most installs:
`companies.requireBoardApprovalForNewAgents` defaults to `false`
(`packages/db/src/schema/companies.ts:21`), and with it false, **neither**
`POST /companies/:companyId/agent-hires` **nor** `POST /companies/:companyId/agents`
creates an approval record at all (`server/src/routes/agents.ts:3139-3359`) — there
is no approval event to attach to in the default configuration.

**Corrected hook point: agent creation, not hire approval.** Both routes converge
on the same underlying agent-creation service call (`server/src/services/agents.ts`,
`svc.create(...)`, aliased `svc` at `server/src/routes/agents.ts:311`). Code-verified
(round-3 review): `svc.create()` is called unconditionally with respect to
`requireBoardApprovalForNewAgents` from both `POST /agent-hires` (agents.ts:3211)
and `POST /agents` (agents.ts:3415) — that flag only changes the resulting status /
whether a hire-approval row is *also* created, not whether `svc.create()` runs. The
grant-request emission attaches **inside `svc.create()`'s own body**, not as a
separate call added after each route invokes it — this is a real, load-bearing
choice, not a wording detail: `svc.create()` has a **third call site**,
`server/src/services/approvals.ts:161` (inside `approve()`, resolving a `hire_agent`
approval whose payload has no `agentId` yet). Hooking inside the body covers that
path too, with no separate code needed per call site; hooking after each call site
instead would silently miss that third path. "CEO-attributed" describes attribution
in the activity log (recorded as taken on the CEO's behalf / under the CEO's
authority), not a literal runtime dependency on the CEO agent's process being
healthy — this is deterministic system code, not the CEO agent's own LLM-driven
heartbeat reasoning.

This resolves three problems:
- **Route coverage (previously Open Question #4):** hooking the shared creation
  service, rather than either route's approval branch, covers both
  `agent-hires` and the board-direct route for free. No longer open.
- **Ordering:** emission happens before the creation call returns, guaranteeing
  the grant request exists before the new agent's first heartbeat can run.
- **CEO single point of failure:** if the CEO agent is budget-paused or its own
  heartbeat is failing (per AGENTS.md's budget-auto-pause invariant), the grant
  request still fires — it isn't the CEO agent's runtime that emits it.

**Implementation note (corrected — round-2 draft was wrong here):**
`svc.create()` already runs inside a `db.transaction`
(`server/src/services/agents.ts:804`), which already does an in-transaction
side-effect after the agent insert (`syncAgentSecretBindings(created, txDb)`,
line 830) — a concrete existing template for "add one more write inside this
transaction." The tool-access-grant approval insert should follow that same
pattern, inside the same transaction, rather than needing new transactional
plumbing. This makes atomicity easier than the prior draft assumed, not an open
build risk.

**Rejection must clean up the paired approval (must-fix, found in round-3
review — not optional).** Because the tool-access-grant approval is created at
agent-creation time, it exists *before* a `requireBoardApprovalForNewAgents=true`
hire is itself decided. `approvalsSvc.reject()` for `hire_agent` already calls
`agentsSvc.terminate(payloadAgentId)` (approvals.ts:225); a rejected hire must
also call the existing `approvalsSvc.cancel(id, reason)` (approvals.ts:124-126,
already built for "paired agent terminated during cleanup") on the tool-access-
grant approval. Without this, every rejected hire leaves a permanently-stuck
approval-queue entry pointed at a terminated agent.

This also sharpens why the fast-track option below is not the "silent auto-bind"
that Constraints rejects: a fast-tracked grant still writes a reviewable
activity-log entry attributed to the CEO and is inspectable after the fact — the
rejected alternative was a bind with *no record at all*. The distinction is
auditability, not automation level.

## Premises

1. The gap is not "agents can't get MCP access" (that machinery works) — it's that
   granting it is a separate, forgettable manual step from hiring. **Agreed.**
2. "CEO agent configures MCP" is a proxy for "the hire flow sets tool-access scope
   at creation time" — it does not require the CEO's own process to call
   gateway/token APIs directly. **Agreed**, and now made explicit in Trigger
   Mechanism above: emission is deterministic system code, CEO-attributed.
3. This reuses the existing role-scoped tool-access profile model; two agents with
   the same role get the same MCP scope, applied automatically instead of manually.
   **Agreed after clarification** (initial pushback was about *timing* — grant at
   spawn, not after — not about wanting per-instance-unique credentials).

## Landscape Check

2026 multi-agent tooling (vMCP-style scoped servers, ToolHive tool optimization,
manager/sub-agent orchestration patterns) converges on: tool surfaces should be
scoped per agent role, AND the manager/orchestrator sets that scope as part of
spawning the sub-agent, not as a follow-up admin task. Paperclip's scoping model
(role-based profiles, resolved fresh per heartbeat) already matches the first half;
this design closes the second half — timing. No premise was overturned by this
research; it reinforces the direction already chosen.

## Approaches Considered

### Approach A: Auto-bind at hire-approval (minimal)
Extend the `agent-hires` approval service: on approval, look up the new agent's
role/team and auto-attach the matching existing tool-access profile(s) via the
current binding service. No new schema.
- Pros: smallest diff, one hook in an existing service, directly kills the
  reported pain.
- Cons: only covers the approval-gated hire path, not the board-direct
  `POST /agents` route; needs a role→profile naming convention that doesn't
  exist yet.
- Rejected as the sole approach: doesn't give an audit trail as a CEO-attributed
  decision, and leaves the board-direct route unfixed.

### Approach B: Catalog-declared defaults (ideal architecture)
Declare a default tool-access profile per role in the teams-catalog `TEAM.md`
templates; unify both creation routes behind one hire-and-provision service that
reads the catalog default and binds it atomically with agent creation.
- Pros: covers every hire path; profile choice becomes a versioned, reviewable
  catalog fact instead of implicit code logic.
- Cons: touches `packages/teams-catalog` + its generated manifest (regen step),
  a real contract/schema change, more surface than A.
- Rejected as the sole approach for this iteration: larger diff than the
  problem currently warrants; still doesn't produce an audit trail as an
  explicit CEO-attributed action.

## Recommended Approach

**Approach C: CEO-attributed governed grant.** Chosen by the user over A/B despite
the flagged risk (see Open Questions). Provisioning becomes an explicit,
CEO-attributed action through the existing approval-gate pipeline: on agent
creation (either route — see Trigger Mechanism), deterministic system code emits
a tool-access grant request for the new hire — defaulting to that role's default
profile (a role may map to more than one profile; the emission grants all of
them, not just one) — logged to the activity log like any other governed CEO
action.

Rationale: this fits the product's existing story that agent-affecting actions
should be visible and attributable, and reuses existing approval-gate,
activity-log, and tool-profile-binding-precedence machinery with no new schema.

## Open Questions

1. **Re-introduction risk — needs an explicit answer before build:** does the
   grant request auto-approve when it exactly matches the role's default profile
   (a genuine deviation still requires a human), or does the hire stay
   blocked/flagged until a human approves the grant? Recommendation:
   auto-approve the default-match case — it still produces the CEO-attributed
   activity-log entry this design cares about, and a human-approval requirement
   on the *common* case reintroduces exactly the "forgettable step" bug this
   design exists to fix. Reserve human approval for genuine deviations.
   **Deviation mechanically defined:** the system always proposes the role's
   default profile(s) — it never invents a "deviation" on its own. A deviation
   arises only when a human, reviewing the pending grant in the existing
   approval queue UI, edits the proposed profile set before approving (grants a
   different/narrower/wider set than the default). That edited-and-approved
   case is what "deviation" means here; it is a human override of the default,
   not a second system behavior to build.
2. **Role→profile naming convention:** how does the lookup map "CTO" (or a
   teams-catalog role) to a specific `toolProfiles` row (or rows — see
   Recommended Approach)? Not yet defined — needed before the lookup can be
   implemented.
3. **No matching profile for a role, and what "blocked" means operationally:**
   if the lookup finds no profile for the new agent's role, the agent record is
   still created (avoids inventing a new agent-instance MCP schema just to gate
   creation) but the pending tool-access-grant approval is left open rather
   than auto-approved — i.e. it lands in the same open/pending approval state
   as a genuine deviation (see #1), visible via existing approval-queue UI,
   with no MCP access granted until a human resolves it. This reuses existing
   approval-pending states rather than adding new agent-status values; confirm
   this matches how `pending_approval`-style states already work for agents
   (per `doc/plans/2026-02-19-ceo-agent-creation-and-hiring.md`) before build.
4. **Pending-grant visibility:** a pending grant (no-match case, or a human is
   slow to approve a deviation) surfaces through the existing
   approval-gate/pending-approvals UI — reusing existing infra, no new
   dashboard. No separate SLA/timeout mechanism is proposed for this iteration.
5. **Backfill (explicitly out of scope for this iteration):** agents already
   hired without a grant are not remediated by this design. If backfill is
   needed, it's a separate follow-up (a one-time sweep against current agents),
   not part of this change.
6. **Role/profile drift after hire (explicitly out of scope for this
   iteration):** if an agent's role changes, or a profile definition is later
   revised, re-syncing an already-granted agent's MCP scope is not addressed
   here. Flagging as a known gap rather than silently ignoring it.
7. **Transactional atomicity — resolved (round 3):** `svc.create()` already
   transacts; add the grant-approval insert inside it, following the
   `syncAgentSecretBindings` in-transaction pattern (see Trigger Mechanism).
   No longer open.
8. **CEO-attribution fallback (found in round-3 review):** "CEO-attributed" is
   only cleanly resolvable when exactly one non-built-in, non-pending, no-manager
   agent has role "ceo" (the same resolution `built-in-agents.ts`'s
   `ensureRootAgentDefaultChangeGrants` already uses). A brand-new company
   hiring its first-ever agent, or a company with a CEO in flux, may have zero
   or multiple candidates. Use the existing `actorType: "system"` fallback
   (precedent: `server/src/services/hire-hook.ts`) when no single CEO-role
   agent resolves, rather than leaving attribution undefined.

## Success Criteria

- A newly hired agent (via either creation route) has its role's MCP profile
  granted, or is left in an explicit, visible pending state (never silently
  unprovisioned, never a status the existing approval UI can't show) — before
  its first heartbeat run. Ordering is guaranteed by the Trigger Mechanism
  (emission happens synchronously as part of the same agent-creation service
  call, before it returns).
- The grant appears in the activity log as a CEO-attributed action, whether
  auto-approved (default-match case) or human-approved (deviation or
  no-matching-profile case).
- A hire with no matching role profile lands in the same visible pending state
  as a deviation, not silently approved unprovisioned.

## Dependencies

- Existing tool-access services: `tool-access.ts`, `tool-access-policy.ts`,
  `tool-profile-binding-precedence.ts`, `tool-gateway.ts`. Note: there is no
  existing "role" scope in the tool-profile-binding model
  (`TOOL_PROFILE_BINDING_TARGET_TYPES` is company/agent/project/routine/
  issue/gateway) — role→profile resolution is new application logic that then
  binds at the existing per-agent scope; it does not reuse a role-level
  binding that doesn't exist yet.
- Existing approval-gate / activity-log infrastructure, including
  `approvalsSvc.cancel()` for the rejection-cleanup path above.
- `server/src/services/agent-permissions.ts`, `server/src/services/agents.ts`
  (`svc.create()`, all three call sites), and the `agent-hires` route/service.
- **UI:** `ui/src/components/ApprovalPayload.tsx` hard-switches on approval
  `type` (`hire_agent`, `budget_override_required`, `request_board_approval`);
  anything else falls through to `CeoStrategyPayload`, which won't render a
  tool-access-grant payload sensibly. A new `type` needs its own case there —
  small, but real, and not covered by "reuses existing server-side machinery."
