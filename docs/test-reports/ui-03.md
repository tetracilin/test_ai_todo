## 2 Summary

All 17 files were read in full and checked against the production components and helpers they exercise (`IssueAssignedBacklogNotice`, `IssueCasesPanel`, `IssueChatThread`, `IssueBlockedNotice`, `IssueDossierPanel`, `IssueDocumentsSection`, `IssueDocumentAnnotations`, `IssueMonitorBanner`, `IssueLinkQuicklook`, and others). Every subject exists in the fork and every assertion matched current behaviour. Baseline: 216 of 216 pass on Windows with no ENV failures. No upstream-only or stale-default assertions (V1) were found. The fork-owned `IssueDossierPanel` test (PC-002 sections, Teable and minio evidence, Vietnamese verbatim captions) is consistent with the fork's dossier contract.

The defects found were isolation (V4) problems: global patches and mock implementations that survive a failed assertion or leak between tests. Seven files were rewritten to fix them. No assertion was weakened, no test was removed, and the test count is unchanged (216).

Verdicts: VALID 5, VALID_WITH_NOTES 5, REWRITTEN 7, OBSOLETE_REMOVED 0, NEEDS_DECISION 0.

No suspected production bug was found.

## 3 Variances (what could not be verified)

* Run host is Windows 11. All 17 files are DOM tests with no POSIX dependency, and all pass here, so there are no ENV variances.
* jsdom does not implement layout, `scrollIntoView` or `matchMedia`. The virtualizer, scroll and popover-position tests (IssueChatThread, IssueLinkQuicklook, IssueDocumentAnnotations) therefore assert on mocked scroll calls and stubbed geometry. They show wiring, not real layout. Real layout is only covered by the Playwright suites, which were not run.
* The after-edit run of the edited files was made in two vitest processes (IssueChatThread alone; the other six together), each in a single process.
* Class-name assertions (`bg-card`, `border-amber-300/70`, `size-6`, token classes) were validated against current component markup but cannot be validated visually.

## 7 Evaluation and recommendations

* Product findings: none. Components behave as the tests describe; the blocker, recovery and monitor copy is internally consistent with `deriveRecoveryCardState` and `buildMonitorSurfaceCopy`.
* Recommend a shared `waitForAssertion` helper (deadline-based, 5s) for `ui/src/test-utils`, replacing the iteration-bounded copies in IssueAttachmentsSection and IssuePropertiesMarkdownWorkProduct, which are the same shape as the CompanySettings flake fixed in #161. Not done here because it would add a shared helper outside the shard's files.
* IssueChatThread.test.tsx (3,900+ lines, 73 tests) should be split by concern (composer, virtualization/scroll, blocked-notice variants, interactions) and given a `renderThread(props)` helper; the repeated prop block is the main maintainability cost. A `scrollHost()` helper would remove five copies of the scroll-host setup.
* Coverage gaps (clear, not added because each needs fixtures beyond the shard):
  * IssueCasesPanel has no test for `casesApi.listForIssue` rejecting (the panel would hide silently), nor for the three role labels (`origin`, `reference`).
  * IssueAssignedBacklogNotice has no test for `resuming` without `onResume`, or for the user-assignee case hiding the "Comments still notify" line (the component hides it; the test only checks the first line).
  * IssueFiltersPopover has two layout-only tests and none for `onChange` (toggling a status, a label or "Live runs only").
  * IssueDossierPanel does not test a document with zero evidence lines (count text for 0).
* In this CI the `unit` job runs these UI files (non-server groups); the edits here do not change any production surface.
