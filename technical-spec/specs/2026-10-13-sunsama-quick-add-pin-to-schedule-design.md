# Spec: Quick Add Task and Pin-to-Schedule (observed in Sunsama)

Status: draft for owner review. Not a backlog item. `backlog.md` PC-xxx entries are written by the product owner with human confirmation, so nothing here edits it.
Date: 2026-10-13
Source: black-box observation of the public Sunsama web app plus its publicly served JS bundles. No Sunsama source was available.

## 1. Purpose

Describe two Sunsama behaviours precisely enough to decide whether and how Paperclip should offer equivalents:

1. **Quick add**: create a task in one gesture from the day view.
2. **Pin to schedule**: turn a task into a fixed block on the day calendar.

This document separates what was **observed**, what was **inferred**, and what is **unknown**.

## 3. Global Constraints

- All requests go to a single GraphQL endpoint, `POST api.sunsama.com/graphql`, one operation per request body with `operationName` and `variables`.
- Record ids (`_id`) are generated by the client, not the server.
- Timestamps are ISO-8601 UTC strings. Display uses the user's timezone (observed UTC+7).
- Every record is scoped by `groupId`.
- Mutations return a trimmed payload (`limitResponsePayload: true`).

## 4. Behaviour: Quick add

### 4.1 Observed

- **Entry point.** An **Add task** row sits at the top of each day column. Clicking it opens a composer anchored over the column. Keyboard hint `A` is shown on the row.
- **Composer controls.** Free-text "Task description", day chip (default: the day being viewed), time estimate (`--:--`), `#channel`, objective, flag, and an insert-position toggle. A "Paste a URL" tip is shown (E2, E7).
- **Submit.** Enter creates the task. The task appears at the top of the day list immediately (E3).
- **Defaults.** Channel defaulted to a pre-existing one (`proposals`). Planned time defaulted to 3:00 in run 1 and 0:30 in run 2. The reason for the difference is **unknown**.
- **Request.** One `createTask` mutation (E5). Fields observed in `variables.task`: `_id`, `groupId`, `taskType: "outcomes"`, `streamIds`, `recommendedStreamId`, `eventInfo: null`, `seededEventIds: null`, `private: false`, `assigneeId`, `createdBy`, `integration: null`, `deleted: false`, `text`, `notes`, `notesMarkdown`, `notesChecksum`, `editorVersion: 3`, and a `collabSnapshot` object (`state.docName` of the form `tasks/notes/<taskId>`, `updates[]`). The log was truncated at 600 characters in run 1, so the full field list is **not** confirmed.
- **After create.** Opening the task shows channel, flag, start day, due, subtasks, actual and planned time, notes, comments, and an activity log whose first entry is "<user> created this" (E-screenshot `06-task-detail.png`).

### 4.2 Inferred

- Optimistic create: the client builds the full record and id, shows it, then sends the mutation.
- Notes are a collaborative document keyed by task id (`collabSnapshot`), so notes editing is designed for concurrent edits.

### 4.3 Acceptance criteria (for a Paperclip equivalent)

1. From the day view, one click or one key opens a composer with focus in the text field.
2. Pressing Enter with non-empty text creates exactly one task and shows it in the list before the server responds.
3. Pressing Enter with empty or whitespace-only text creates nothing.
4. The new task carries the day it was created from, a default channel/project, and a default estimate. The defaults are configurable or documented.
5. A failed create is visible to the user and does not leave a phantom task.
6. The same `_id` is never submitted twice for one create (retry is idempotent).

## 5. Behaviour: Pin to schedule

### 5.1 Observed

- **Projected time.** For a task with an estimate on today's date, the calendar shows a pink dotted block labelled with the task, starting at the current-time line and lasting the task's estimate. Its start slid forward with the clock (5:45 pm to 5:50 pm between screenshots), so it is not stored (E3, E4).
- **Hover card.** Shows title, time range, channel, then "Projected time", "Flexible, non-blocking", "Only visible to you in Sunsama", and a **Pin to calendar** action (E4, E8).
- **Pin (run 2, manual).** Sent `createCalendarEvent` (E6). The event: `status: "scheduled"`, `service: "sunsama"`, `title` copied from the task, `date.startDate`/`endDate` as UTC (30 min, matching the 0:30 estimate), `streamIds` copied from the task, `seedTask: {_id, groupId}` linking back to the task, `scheduledTo[]` and `organizerCalendar` naming an internal `sunsama-<uuid>` calendar, all external `serviceIds` null, `transparency: "opaque"`, `visibility: "default"`, `visualizationPreferences[].settings.blockProjections: null`.
- **Result in UI.** The task card shows an orange start-time badge (4:50 pm after the move) and a solid orange block appears on the calendar. A tip reads "Once scheduled, tasks stay pinned to a specific time" (`20-after-manual.png`).
- **Move.** `updateCalendarEvent` with `eventId`, a new `date`, `lastModified`, `sendEmails: false`, `skipReorder: true`. The block keeps its length.
- **Which gesture sent the pin** (button vs drag) is **unknown**; the log does not record it.

### 5.2 Inferred

- A pinned task is a calendar event on an internal calendar with a back-reference to the task, not a field on the task.
- The projection is computed client-side from the estimate and the clock; only the pin persists anything.
- The `skipReorder` flag suggests moving an event can otherwise renumber or reorder neighbouring items.

### 5.3 Unknown

- Whether unpinning deletes the event or only clears the link (`deleteCalendarEvent` exists in the bundle).
- What happens to the task's estimate when the pinned block is resized.
- Conflict handling when a pin overlaps an existing event.
- Whether tasks without an estimate can be projected or pinned.
- Behaviour on days other than today, where there is no current-time anchor.

### 5.4 Acceptance criteria (for a Paperclip equivalent)

1. A task with an estimate on today's date shows a clearly "tentative" block that is not persisted and visibly differs from a pinned one.
2. Pinning persists one scheduled record with a start, end, and a link to the task. Pinning the same task twice does not create two records.
3. Moving a pinned block changes only its start and end and preserves its duration.
4. Pinned blocks count as busy time. Projected blocks do not.
5. Pinning and moving send no notifications by default.
6. Deleting the task removes or orphans-safely its pinned block (choose one and document it).

## 6. Review Focus (cases the observations imply but the criteria above do not pin)

Most likely to bite first:

1. **Timezone and day boundary.** Task created near midnight, or a user whose timezone differs from the server: the projected block and the stored UTC range must land on the same local day.
2. **Double submit.** Enter pressed twice, or the network retrying a create: expect one task.
3. **Pin with overlap.** Pinning into a slot already occupied: expect a defined result (allow, shift, or reject), not silent overlap with no indication.
4. **Task with no estimate.** Expect a documented default or a disabled pin action, not a zero-length block.
5. **Delete or complete a pinned task.** Expect the block to disappear or update with the task, not remain as an orphan.

## 7. Owner Decisions (2026-10-13)

1. **Task equivalent.** A Paperclip issue is the equivalent of a Sunsama task, with a schedule and an estimate. Owner believed this was not implemented. Section 7a shows it is partly implemented.
2. **Pinned block.** A pinned block becomes an **event, its own entity**. Owner's model: an issue with a scheduled date is an event, and the event is pinned to the calendar on that date. Section 7a shows this conflicts with the current data model, so it is open until the owner resolves it.
3. **Calendar sync (Google, Microsoft).** Out of this MVP. Google Calendar sync is "someday" and was added to `roadmap.md` (FUTURE). Sunsama's pinned events carry null external ids, so sync is not needed to reproduce the behaviour in section 5.
4. **API.** An API is wanted, and the owner's company has an API-driven timesheet-to-payment tool that may consume it. **Decision on API design is held** until the owner has reviewed the evidence in section 7b.

## 7a. Verified current state of scheduling in this repo (read 2026-10-13, branch `develop`)

Scheduling is **partly built** already, centred on the issue rather than on a separate event.

Consequences for this spec:

- Pin-to-schedule as Sunsama does it (a separate calendar-event record linked back by `seedTask`) is **not** how Paperclip models it today. Paperclip stores the schedule as fields on a 1:1 side table of the issue. Owner decision 2 asks for a separate event entity, which would change that model.
- There is **no estimate** and **no actual time** on issues (no such column in `packages/db/src/schema/issues.ts`). `scheduled_duration_minutes` is the only duration. Sunsama's "planned" versus "actual" time has no counterpart here.
- No quick-add composer or projected-time block was seen in `Today.tsx` or `Schedule.tsx` by grep. I did not run the UI, so this is "not found in code", not "confirmed absent".

## 7b. Verified evidence on API and activity-logging structure (for the held API decision)

Read from code on 2026-10-13. Nothing here was run against a live server.

**Conventions every endpoint is expected to follow** (`AGENTS.md` section 8): base path `/api`; board access is full-control operator context; agents use bearer keys (`agent_api_keys`, hashed at rest) and may not cross companies; new endpoints must apply company access checks, enforce board-vs-agent permissions, write activity log entries for mutations, and return consistent `400/401/403/404/409/422/500`.

**How a mutating route does it today** (`scheduling.ts`, `PUT .../scheduling`):

1. `validate(schema)` middleware on the body, then `assertCompanyAccess`, then an `access.decide({action: "tasks:assign", ...})` permission check.
2. The service performs the write.
3. A separate `logActivity(db, {...})` call records `action: "issue.scheduling_updated"`, `entityType: "issue"`, `entityId`, and `details`.

**The activity log is an audit trail, not a versioned integration contract:**

- Table `activity_log` has `actor_type`, `actor_id`, `action` (free text), `entity_type`, `entity_id`, optional `agent_id`, `run_id`, `responsible_user_id`, and a free-form `details` jsonb. Indexed by company+time, company+agent+time, company+responsible user+time, run id, and entity.
- `actorType` is one of `agent`, `user`, `system`, `plugin`.
- `details` is passed through a redactor before it is stored, and may censor the current username when the instance setting is on.
- `responsible_user_id` is resolved in order: the acting user, the heartbeat run's responsible user, the issue's responsible or creating user, the agent key's responsible user, then the company default. This is how an action by an agent is attributed to a person.
- After the insert, `logActivity` publishes a live event `activity.logged` and, if the action maps to one, a plugin event. It also enqueues Discord notifications to an outbox table (`integration_event_outbox`) with an `idempotency_key`, inside a try/catch so that a failure never blocks the source action.

**Gaps relevant to a timesheet or payment consumer (all observed in code):**

1. **Scheduling actions emit no plugin or Discord events.** The plugin mapping `ACTIVITY_ACTION_TO_PLUGIN_EVENT` covers comments, documents, blockers, approvals and budgets, and the Discord mapping covers issue created, status, assignee, priority, comment, blocked and completed. `issue.scheduling_updated` and `issue.scheduling_cleared` are in neither, so an external system cannot subscribe to them today.
2. **The activity read API cannot support reconciliation well.** `GET /companies/:companyId/activity` accepts only `agentId`, `entityType`, `entityId` and `limit`, ordered newest first and capped by `normalizeActivityLimit`. There is no `since`, no action filter and no cursor, so a consumer cannot reliably page through everything after a checkpoint.
3. **The log write is not atomic with the change.** In the scheduling routes the service write and `logActivity` are two separate calls. `logActivity` has a `postCommitPublications` parameter that suggests a transactional pattern exists elsewhere, but the scheduling routes do not use it. A crash between the two calls would leave a change with no log entry. This is an inference from the call order, not a reproduced failure.
4. **Scheduling activity records only the new values.** `details` for `issue.scheduling_updated` carries `scheduledAt`, `deferUntil` and `scheduledDurationMinutes` only. The `issue.updated` path, by contrast, carries `_previous`, which the Discord logic reads. So scheduling changes cannot be diffed from the log.
5. **No timesheet or payment code exists in the repo.** A search of `server/src`, `packages/db/src` and `packages/shared/src` found no timesheet, payroll or payment code. The only related document is `doc/plans/2026-03-14-billing-ledger-and-reporting.md`, which concerns model and provider spend (`cost_events`), not human time. The company's timesheet tool and its API contract were **not** seen.
6. **Idempotency exists but is local.** Issue creation can deduplicate by an idempotency key, and the Discord outbox uses keys, but no generic `Idempotency-Key` header convention was found for the scheduling routes.
7. **An OpenAPI document exists** (`GET /api/openapi.json`, built in `server/src/routes/openapi.ts`) and lists the activity routes. Whether the scheduling routes are in it was not checked.

## 7d. Further findings from planning (read 2026-10-14)

Read from code. Nothing here was run.

1. **Resize sends one request per mouse move.** In `ui/src/components/ScheduleAgendaGrid.tsx`, `handleResizeMove` calls `onResizeItem` on every `mousemove`. `Today.tsx` and `Schedule.tsx` wire that to a mutation that sends `PUT .../scheduling`. Each request writes one `issue.scheduling_updated` activity row. A single drag may therefore write many rows. This is the inference from the code; the number of rows per drag was not measured.
2. **Create-and-schedule is two requests.** `Schedule.tsx` (`createAndScheduleMutation`) calls `issuesApi.create` with the title "New task", then `schedulingApi.upsertIssueScheduling`. If the second call fails, an unscheduled "New task" remains.
3. **An estimate without a time cannot be shown.** `Today.tsx` filters items on `scheduledAt`, so an issue with only `scheduledDurationMinutes` does not appear in the grid. Both fields are nullable, so the table already allows the state.
4. **Scheduling routes are not in OpenAPI.** `server/src/routes/openapi.ts` has no match for `scheduling` or `scheduled-issues`, although the activity routes are listed. A client reading `GET /api/openapi.json` cannot discover scheduling today.
5. **No tentative state exists.** Any `scheduledAt` is firm. Nothing in the UI draws a projected block.

## 7c. Questions that block the API decision

1. What does the timesheet-to-payment tool need from Paperclip: a pull API (poll for completed or scheduled work), push events (webhook or outbox), or both? Please share its API contract or a sample payload.
2. Is "actual time" a Paperclip concept, or does the timesheet tool own it? Today there is no actual-time field.
3. Is a scheduling change ever a payable fact, or only completed work? That decides whether gaps 3 and 4 above are acceptable.
4. Resolve decision 2 against section 7a: keep the 1:1 side table and add event semantics to it, or introduce a separate event entity and migrate `issue_scheduling` forward-only.

## 8. Next Step: implementation plan

Do not write the implementation plan yet. It depends on 7c: the data-model choice (question 4) fixes the files and interfaces, and the API shape (questions 1 to 3) fixes the auth, activity-logging and event work. Per `CLAUDE.md`, a data-model change touches `packages/db`, `packages/shared`, `server` and `ui` together, and any migration must be forward-only and backward-compatible with the previous release for one cycle. Because scheduling already exists, the plan will be a delta against section 7a, not a greenfield build.
