## Problem Statement

An embedded-firmware programmer runs agents on a Paperclip kanban project. Four pains were reported:
1. Tasks must run in the order the human chooses, with dependencies respected.
2. The approver has no UI to act on `in_review` output.
3. The project needs a work-in-progress (WIP) limit.
4. Assigning a task to an agent starts it (`in_progress`) instead of leaving it in Todo; the human plans in backlog, clarifies to todo, and wants an explicit "ready" signal.

Reframed during the session: this is not a scheduler. It is a human-ranked queue with a release gate and a per-project compute budget.

## Demand Evidence

None observed. The four pains come from the engineer telling the requester what they want (D3, answer C). No watched run, no incident, no cost figure. Treat every pain as a claim until the assignment below is done.

## Status Quo

The human is the scheduler, by choice: "the human can prioritize the tasks queue". They assign issues by hand and, because assignment starts the agent, they control timing by when they assign. No measured cost (minutes of babysitting per task) yet.

## Constraints

- Agents run local embedded toolchains; local RAM is the binding limit. Concurrency today is capped per AGENT only (`server/src/services/heartbeat.ts:13914`, `availableSlots = policy.maxConcurrentRuns - runningCount`). Nothing caps a project or host.
- Dependency holding already exists (`issue_relations` type `blocks`; `heartbeat-dependency-scheduling.test.ts`: "keeps blocked descendants idle until their blockers resolve").
- Overflow wakes are queued first-in-first-out, not by human rank.
- Migrations must be forward-only and backward-compatible for one release cycle (CLAUDE.md). New columns must be nullable or defaulted.
- Pipeline rules: feature/* branch from develop, PR only; server changes need the relevant server suite run locally (t3-ci runs none).
- Separate from the merged calendar scheduling spec (#177, Sunsama-style quick-add/pin); do not merge the two.

## Premises

1. The human is the scheduler. The product is a ranked queue; no auto-ordering engine. Dependencies only block a start.
2. Assigning never starts work. Backlog = planned, off-limits to agents. Todo = ready; an agent may pull it when capacity is free, in rank order. The separate "ready for dev" tag is dropped (one source of truth). Revisit if a real case needs a todo that agents must not touch.
3. (Revised after second opinion) WIP is a per-project run cap expressed as the SUM of per-task weights (`slot_weight`, default 1) of running tasks. It stands in for the human's RAM budget. No live memory measurement in v1, but peak RSS per run is logged to calibrate weights.
4. Wedge = gate + rank + weighted cap + pull step. Review inbox, with its own review-capacity cap, is the next slice.
5. Before building, watch one real run and record the cap at which the machine struggles.

## Cross-Model Perspective

## Approaches Considered

- A. Gate + instrument (minimal): assignment gate and peak-RSS logging only; no rank or enforced cap. Rejected as the first slice because the human still hand-feeds Todo, but it is the fallback if the first real run shows uniform cost and rare reordering.
- B. A queue you trust (CHOSEN): see below.
- C. Dispatcher as a routine (lateral): scheduled routine releases Todo by rank and capacity. Rejected: cannot fix assignment-starts-work, and polling creates a second source of truth.

## Recommended Approach

B. Concretely. Schema changes are additive (nullable or defaulted columns). The behavior change is OPT-IN per project, so existing projects keep today's behavior.

Defaults below were chosen by the author in response to spec review; each is overridable by the owner.

- Schema: `projects.queue_mode` (bool, default false), `projects.max_run_weight` (nullable int; null = no project cap), `issues.rank` (fractional key, nullable), `issues.slot_weight` (int >= 1, default 1), and a per-run `peak_rss_bytes` record (see Instrumentation).
- Opt-in cutover: with `queue_mode` false, assignment and wake paths behave exactly as today. When an owner turns it on for a project: issues already `in_progress` are left alone and finish normally; wakes already queued are not cancelled; only new assignments and new wakes follow queue rules. Turning it off restores old behavior with no data change.
- Queue rules (queue_mode true):
  - Assigning an issue never starts a run and never sets `in_progress`. Backlog issues are never pulled.
  - Eligible for pull: Todo issues that have an assignee agent and no unresolved `blocks` blocker.
  - Order: strict rank, head of line waits. If the top eligible issue does not fit the project cap, the pull waits for capacity and does NOT skip to a lower-rank issue (the human's order is the point; accepted cost: the machine may idle). Exception: an issue whose assigned agent is at its own `maxConcurrentRuns` is skipped for now, because that is agent busyness, not a human ranking decision.
  - Both caps must pass: the agent's `maxConcurrentRuns` and the project's `max_run_weight`.
  - Oversize weight is rejected at every entry point, never silently stuck: a write that sets `slot_weight` above `max_run_weight`; a status change into Todo or an assignment for an issue whose weight exceeds the cap; and a write that lowers `max_run_weight` below the weight of ANY non-terminal issue in the project (backlog, todo, in_progress, in_review, blocked). Each returns a clear error naming the offending issues.
  - Non-Todo and retry wakes (a comment or mention on an `in_progress` or `in_review` issue, a retry of a failed run, a blockers-resolved follow-up on an issue that already ran): these count toward the running weight while their run executes. When capacity is unavailable they are NOT rejected; they queue first-in-first-out and are admitted ahead of new Todo pulls, because finishing started work frees capacity sooner and a retry must not starve behind new work. They still never exceed the cap.
  - Trigger ("Todo release" and "run completion"): the pull runs when a run for the project ends, when an issue enters Todo or its rank changes, when a blocker resolves, and when `max_run_weight` is raised.
- Serialization: the pull locks the project row (`SELECT ... FOR UPDATE`) while it sums running weights and claims the chosen issue, so two concurrent pulls cannot both pass the sum check. Every path that starts a run in a queue_mode project must go through this one admission function: assignment wake, comment/mention wake, retries, blockers-resolved wake, scheduled heartbeat. The implementer enumerates the run-start sites in `heartbeat.ts` before coding; the default is no exemptions, except an explicit, activity-logged human "run now" override.
- Rank rules: rank is per project and orders Todo. Null rank sorts after all ranked issues, by `created_at`. An issue entering Todo gets a rank at the bottom unless the drop position sets one. A drag writes a key between its neighbours; when the gap is exhausted the project's Todo keys are rebalanced in one transaction. Concurrent reorders are last-write-wins per issue; ties break by `created_at`.
- Weight write path: `PATCH` issue `slotWeight` (human only; agents cannot set it), activity-logged, with a numeric field on issue detail (default 1). Until RSS data exists, weights are set by the engineer from experience; leaving all at 1 is a flat count.
- Routes: PATCH rank, PATCH `slotWeight`, PATCH project `queueMode` and `maxRunWeight`, all activity-logged.
- UI: drag-to-reorder on the Todo column, project cap and queue-mode controls, weight field on issue detail, "running X/N" badge on the board header, "queued" mark on Todo cards waiting for a slot or a blocker. Use only design tokens (`pnpm check:token-gates`).
- Instrumentation (this slice): for local process adapters on the host OS, sample RSS of the run's process tree (root pid plus descendants) every 5 seconds and store `run_id`, `peak_rss_bytes`, `sample_count`, `measured` (false with a reason when unsupported, for example remote or container adapters). Other adapters and cross-host measurement are out of scope. This is the evidence for premise 5 and the calibration data for weights.
- Tests: pull function (rank order, head-of-line wait, blocked skipped, agent-cap skip, project cap across two agents, concurrent-pull race on the project lock); assignment never starts a backlog or Todo issue in queue_mode; queue_mode false is unchanged.
- Skip in this slice: review inbox, "ready for dev" tag, auto-ordering, live memory-based throttling, multi-host pools, cross-host RSS.

Visual mockups were skipped (design binary not set up on this machine). The board layout follows the existing status columns.

## Success Criteria

- Assigning a backlog or todo issue to an agent never starts a run by itself (test).
- With a project cap set in queue_mode, the sum of running weights never exceeds it, across all agents (test with two agents). The only exception is the explicit, activity-logged human "run now" override, which counts toward the sum and may exceed the cap; it is not used by any automatic path.
- Pull order follows rank and skips blocked issues (test).
- Every run on a supported local process adapter records `peak_rss_bytes`; every other run records `measured=false` with a reason (test both).
- On the first real 5-6 task run at caps of 2 then 4, the engineer reorders by drag and does not hand-start tasks; the cap at which the machine struggles is recorded.

Question D3:
D3 — Which lock should serialize the project cap check and the claim?
Project/branch/task: develop, human-ordered resource-capped run queue (approved design doc; scope per D1, D2).
ELI10: Before a run starts, the server must add up what is already running in the project and only then start the new run. If two agents do that at the same moment, both can see room and both start, going over the cap. A lock makes them take turns. The existing lock only covers one agent and lives in the server's memory, so it cannot stop two different agents. You choose where the new lock lives.
Stakes if we pick wrong: with the wrong lock the cap can be exceeded under load, and the engineer's machine runs out of memory, which is the exact failure this feature exists to prevent.
Recommendation: A because a database lock also works if the server is ever run as more than one process and has no timeout that lets a stale holder through, while the in-memory lock silently breaks the cap in both cases. Evidence that would change my mind: you are certain the server stays a single process and accept a bypass after 30 seconds.
Completeness: A=9/10, B=6/10
Pros / cons:
A) DB advisory lock in a transaction per project claim (recommended) (human: ~1.5 days / CC: ~1 hour)
  ✅ Holds across processes and has no stale bypass, so the cap is a hard guarantee.
  ❌ Adds a transaction and an advisory lock to the hot run-start path, which needs a race test.
B) In-memory per-project lock like agent-start-lock (human: ~0.5 day / CC: ~20 min)
  ✅ Simplest, matches the existing pattern, and cheap on the hot path.
  ❌ Breaks across processes, and the 30 second stale bypass can let two runs past the cap.
Net: A makes the cap a real guarantee at the cost of one transaction; B is simpler and can leak past the cap.
Header: Cap lock
Options:
A) A: DB advisory lock (recommended)
Transaction per project claim holding a Postgres advisory lock on the project id around the weight sum and the claim; no stale bypass; over-cap runs left queued; queued runs of all project agents promoted when a run ends.
B) B: In-memory lock
Per-project in-process lock like agent-start-lock with its 30 second stale bypass; over-cap runs left queued; queued runs of all project agents promoted when a run ends.

- Cap lowered below running weight: running runs continue; new claims wait; covered.
- DB unavailable during the claim transaction: claim fails, run stays queued; covered by the deferred outcome test.
