# Design: Make the t3-nightly full vitest suite complete, then gate it on PRs

Generated by /office-hours on 2026-10-09
Branch: develop
Repo: tetracilin/test_ai_todo (hard fork of paperclipai/paperclip)

Mode: Startup (intrapreneurship)

## Problem Statement

`slow-tests` in `.github/workflows/t3-nightly.yml` has failed on every one of the 46 runs
from 2026-09-02 to 2026-10-09 (22-30 min each). The full vitest suite has never completed
once. The forking decision did not break the tests directly. It removed the machinery that
kept them green, and left a runner that hides how many tests are actually red.

## Evidence (from the run logs, run IDs in parentheses)

1. **The suite never gets past the first red file.** `scripts/run-vitest-stable.mjs:306`
   calls `process.exit()` on the first non-zero vitest invocation. `pnpm test:run` runs
   general lanes first, then 123 serialized route suites as separate invocations.
   - 42 of 46 runs died in the first lane (`general-server`, one big invocation).
   - 4 runs reached the serialized lane. Best: 101 of 123 (35407412087, 35477371749, died
     on `issue-subtask-progress-routes`). Latest two: 8 of 123 (37871306876, 37753743203,
     died on `agent-adapter-validation-routes`).
   - 38 serialized route suites have never executed in nightly, including fork-owned ones:
     `teable-*-routes`, `teams-catalog-routes`, `secrets-routes-claude-oauth-service`,
     `plugin-*-authz`, `workspace-runtime-*-authz`.
2. **Each night shows one failure, then hides the rest.** Failure history is a relay race:
   `cli-invocation-safety` (Sep 2-3) then `server-startup-feedback-export` + `status-cards`
   (Sep 4 - Sep 17) then `workspace-runtime` (Sep 17) then `issue-subtask-progress-routes`
   (Sep 18-19) then `server-startup-feedback-export` alone (Sep 20 - Oct 8) then
   `agent-adapter-validation-routes` (Oct 8-9). Fixing one reveals the next. Nobody sees the
   total count.
3. **The failures are fork drift, not product bugs.**
   - Oct 8-9: `agent-adapter-validation-routes.test.ts:319,375,439,593` expect
     `"Available adapters: hermes_gateway"`. `server/src/adapters/registry.ts:725` now
     defaults the selectable list to `hermes_gateway, claude_local, hermes_local`
     (PRs #118, #140). The test was written when Hermes Gateway was the sole adapter and
     never sets `PAPERCLIP_SELECTABLE_ADAPTER_TYPES`.
   - Sep 20 - Oct 8: `server-startup-feedback-export.test.ts` hand-mocked `@paperclipai/db`;
     new imports in the real service graph (`heartbeatRuns`, `agentWakeupRequests`,
     `documents`) hit the mock at module load. Red for 19 consecutive nights, fixed by #156
     on Oct 8, still open in the latest runs because they ran on stale SHA `1814b0dc`.
   - Sep 13-17: `workspace-runtime` flake from CPU starvation (documented in the runner
     comment at `run-vitest-stable.mjs:61-71`).
   - Noise on every run: 1-12 `EADDRINUSE` lines (port collisions in embedded servers),
     `plugin-worker-manager` `Test timed out`.
4. **The gate that kept this green upstream was removed.** Upstream `pr.yml` sharded the
   server suites across a matrix on every PR. The fork's `t3-ci.yml` `unit` job runs only
   `general-workspaces-a` and `-b` (non-server). CLAUDE.md states it plainly: green CI does
   not mean server tests pass; PRs #80 and #81 regressed this way. Server tests only run
   post-merge, one nightly at a time, serial in one job.
5. **Coverage has silently shrunk and diverged.**
   - `vitest.config.ts` lists 5 projects the runner's hard-coded `nonServerProjects` omits:
     `adapter-cursor-cloud`, `adapter-cursor-local`, `adapter-grok-local`,
     `adapter-kimi-local`, `adapter-pi-local` (~25 test files that no lane runs).
   - Fork packages with tests are in neither list: `hermes-paperclip-adapter` (10 files),
     `plugin-kubernetes` (21), `tailscale-https-broker` (12), `teams-catalog` (2), several
     sandbox plugins. `adapter-hermes-gateway`, the adapter your product now depends on, has
     0 test files.
6. **Cost.** ~25 min of `ubuntu-latest` per night to learn one fact. e2e is a separate job
   now and passes; the Discord alert is unset (`DISCORD_WEBHOOK_URL`), so red goes unseen.
   The nightly's own comment says e2e "has never executed" because vitest failed first;
   that was fixed by splitting jobs and is now green.

## Why the "full vitest suite can't be run"

Four causes, in order of weight:

| # | Cause | Type | Where |
|---|-------|------|-------|
| 1 | Fail-fast runner turns N failures into 1 visible failure per night | Structural | `run-vitest-stable.mjs:306` |
| 2 | Server suites left the PR gate, so fork-policy PRs stale them post-merge | Process | `t3-ci.yml` vs removed `pr.yml` |
| 3 | Hard-coded project list drifted from `vitest.config.ts`; fork packages in neither | Config | `run-vitest-stable.mjs:20-33`, `vitest.config.ts` |
| 4 | Genuine test debt: stale assertions, over-specified mocks, port/CPU contention | Test quality | see Evidence 3 |

Not a cause: hard fork itself, pnpm version, Node 24, missing `plugin-sdk` build (fixed with
`ensure-build-deps`; no `ERR_MODULE_NOT_FOUND` in the last 46 logs), or the Postgres
embedded runtime (works; hook timeouts raised in `server/vitest.config.ts`).

## Status Quo

Manual click-through of staging (:33130) after deploy. It cannot see route-level authz or
adapter-policy regressions. The cost is blind spots, not hours.

## Narrowest Wedge (your answer)

"One green run, then gate." One complete, green nightly, then keep it green with a PR gate.

## Premises (all agreed)

1. Full suite has never completed; 38 route suites never ran in nightly.
2. Main cause is structural (fail-fast runner collapsed from a per-shard PR matrix into one
   serial job), not flakiness.
3. Most failures are fork drift, not broken product.
4. Coverage has silently shrunk (5 adapter projects + fork packages unreferenced).
5. "Green once" re-rots within a week unless gated on PRs.

## Approaches Considered

- **A: run-to-completion + fix reds.** Rejected as the end state: no gate, re-rots.
  Kept as step 1 of B.
- **C: fork-contract tests + changed-files gate.** Rejected: changed-file selection misses
  import-graph breaks like the feedback-export mock gap. Idea kept (see step 2 below).
- **B: A, then sharded PR gate (CHOSEN).**

## Recommended Approach: B (human ~1 week / CC ~half day + human review of the ci PR)

Step order matters; each step is its own PR off `develop` per the CI/CD rules.

1. **PR `fix/vitest-run-to-completion` (app code, no workflow files).**
   - `run-vitest-stable.mjs`: collect exit codes, keep running every invocation, print a
     final table (invocation, status, duration), exit 1 if any failed. Add `--bail` to keep
     today's behaviour for local use. Extend `scripts/__tests__/run-vitest-stable-shard.test.mjs`.
   - Derive `nonServerProjects` from `vitest.config.ts` minus `server`, so the two lists
     cannot drift; add a unit test asserting runner projects == config projects.
   - Land it, let one nightly run, read the complete red list. Expect more than the 4 tests
     seen so far: 38 never-run suites are unknown.
2. **PR(s) `fix/stale-server-tests` (one per cluster).**
   - `agent-adapter-validation-routes.test.ts`: set `PAPERCLIP_SELECTABLE_ADAPTER_TYPES=
     hermes_gateway` in `beforeEach`/restore in `afterEach`, or assert against
     `listSelectableServerAdapters()`. Do not hard-code the default list in tests.
   - Mock gaps: use `importOriginal` partial mocks (pattern from #156).
   - Quarantine true flakes (`workspace-runtime`, `plugin-worker-manager`, `EADDRINUSE`) with
     an explicit, dated skip list, never "retry until green".
3. **PR `fix/fork-package-tests`.** Add `hermes-paperclip-adapter`, `adapter-hermes-gateway`
   (write the missing tests), `tailscale-https-broker`, `teams-catalog` to
   `vitest.config.ts` and the runner.
4. **PR `ci/server-test-gate` (labelled `ci`, human review, pipeline files only).** Add a
   `server-tests` matrix job to `t3-ci.yml` using the existing `--mode general --group
   general-server --shard-index/--shard-count` and `--mode serialized` flags and the
   duration manifests (`scripts/*-shard-durations.json`). Shard to roughly 8, target
   under 8 min wall clock. Then add `server-tests` to the required checks on `develop`.
   Update CLAUDE.md "Green t3-ci does NOT mean server tests pass" accordingly.
5. **Nightly stays as the full-suite backstop** and gets the Discord webhook set.

## Success Criteria

- One nightly run with `slow-tests` conclusion `success` and the final table showing
  every vitest project and all 123 serialized suites executed.
- A deliberately broken server test on a throwaway PR is blocked by `server-tests`.
- Seven consecutive green nightlies, or each red traced to a named quarantined test.
- Runner project list equals `vitest.config.ts` (unit-tested).

## Distribution Plan

Existing pipeline covers it: `feature|fix|ci/*` PR, `develop`, nightly. Workflow and
`deploy/` changes only in the separate `ci` PR (step 4).
